# Desktop stack research

**Scope:** Windows-first command center with an embedded real AGY terminal, an existing separate FlowState app, local data, Obsidian, and a possible future phone/cloud companion. Reviewed 6 November 2026. This is research, not a final stack decision or a production security assessment. **Later update:** [stack proposal](stack-decision-proposal.md#new-local-smoke-tests) records subsequent Electron and Tauri smoke tests and their important failures/limitations; where this note refers to those tests as future work, the newer results take precedence.

## What is already demonstrated on this machine

- The earlier [AGY feasibility report](antigravity-feasibility-results.md) records a browser-hosted terminal with actual AGY, interactive input, a custom MCP marker, and an observed brief resize redraw issue. The probe uses `xterm.js`, `node-pty`, a Node service, and a WebSocket. This demonstrates that combination in the test environment; it does **not** demonstrate a packaged Electron app, an integrated Tauri terminal, or a production-grade bridge.
- FlowState's existing source is Tauri v2, Rust, React, and TypeScript. Its `package.json` and the isolated FlowState experiments are consistent with this; see [end-to-end results](end-to-end-prototype-results.md). It has not established a supported API between two apps. Selecting Tauri for the dashboard would not automatically give that dashboard access to FlowState's internal commands or state.
- The copied FlowState proof had around **3.7 GiB of development build cache**. This is one existing copied build, not a clean apples-to-apples benchmark for a new app and not installed app size. A separate measurement is needed for each candidate on the same hardware and feature set.

## Candidate A: Electron + React + TypeScript

- Electron ships a desktop runtime composed of Electron, Chromium, and Node.js. A web UI can stay in React/TypeScript while privileged process, local files, the PTY host and application backend use the Node ecosystem. Its [security guidance](https://www.electronjs.org/docs/latest/tutorial/security) confirms the shipped components and advises isolation, process sandboxing, narrow IPC, and avoiding untrusted content with Node privileges.
- [node-pty](https://github.com/microsoft/node-pty) provides pseudo-terminal access and Windows support and was used in our prior Node-based AGY probe. This is a native module, **not** a pure TypeScript solution. Electron documents that [native modules often need Electron-specific binary compatibility or rebuilds](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules). Windows C++ build tooling or suitable prebuilt binaries may be needed. Test the exact versions and packaging; do not assume simply reusing `node_modules` is enough.
- Potential advantage for this product: the previously tested terminal and much of the dashboard can use one main programming language and a familiar frontend. A future maintainer or AI can navigate TypeScript across many modules, although robust process isolation and native integration still require expertise. This is an assessment, not a measured developer-productivity result.
- Potential cost: bundling Chromium and Node adds installed/runtime footprint relative to using the operating system webview. Actual disk, RAM and startup must be measured for the chosen app. Staying in TypeScript does not automatically solve local security, data recovery, or the separate FlowState bridge.

## Candidate B: Tauri v2 + React + TypeScript + Rust

- [Tauri's architecture](https://v2.tauri.app/concept/architecture/) uses Rust for the core and an OS webview for the interface; [on Windows that is WebView2](https://v2.tauri.app/reference/webview-versions/). A typical packaged Tauri app doesn't bundle a separate browser engine, although deployment choices can include a fixed WebView2 runtime; see its [Windows installer options](https://v2.tauri.app/distribute/windows-installer/).
- Tauri's frontend-to-core [IPC/process boundary](https://v2.tauri.app/concept/process-model/) is a good place to restrict privileged operations, but security depends on the actual commands, permissions, and implementations. As with Electron, prototype loopback endpoints must not be exposed as unrestricted product APIs.
- There are two broad PTY routes to investigate: a Rust PTY implementation such as [portable-pty](https://docs.rs/portable-pty/latest/portable_pty/), or a [separately bundled sidecar](https://v2.tauri.app/develop/sidecar/) containing a Node/native PTY bridge. The shell plugin supports launching processes, but the need is an actual interactive pseudoterminal with correct resize and keyboard behavior; ordinary process pipes are not established as equivalent. Neither Tauri option has been proven here as a packaged AGY terminal.
- Potential advantage: the dashboard uses the same broad desktop technology as FlowState, and a compact delivered executable is plausible. Potential costs: TypeScript plus Rust/IPC and Rust build artifacts; a Node sidecar also introduces Node runtime/packaging, partially offsetting the smaller-runtime advantage. The 3.7 GiB existing cache is concrete evidence that this concern matters here, not proof every Tauri project will consume exactly that amount.

## Candidate C: Local web application plus separate local helper

A browser interface and Node local service could reuse much of the prior terminal probe. This has not been validated as the first-release product and is not just a static website: the helper would own the privileged terminal, filesystem, local data, and integration communication. The service would need a secure local access design and reliable launch/reconnect behavior. It may make web UI sharing easier to explore, but its local helper and session/security lifecycle add operational complexity. The probe is not evidence that a browser alone can access the needed Windows terminal or FlowState capabilities.

## Local storage

SQLite is a plausible local structured-data store for goals, projects, and approval records; keep Obsidian reviewer files user-readable. The exact Node or Rust adapter is not decided. Native SQLite modules have the same packaging/ABI concerns as other native addons; Node's [built-in SQLite API documentation](https://nodejs.org/api/sqlite.html) should be checked against the **Node version embedded in the Electron release actually selected**, including its stability and runtime support. A SQLite database does not provide phone/cloud sync by itself; that needs separate identity, conflict, privacy, and backup design.

## Suggested decision and next evidence

**Provisional recommendation:** Compare Electron/React/TypeScript against Tauri/React/TypeScript on this user's actual terminal and disk constraints, with Electron a sensible candidate if fewer language boundaries and a Node-based AGY host matter most, and Tauri a strong candidate if delivery footprint and reuse of existing Rust skills outweigh build-cache and integration cost. This is a tradeoff, not proof one is universally superior.

Before a final commitment, a controlled small Windows spike should package the same minimal app in both candidates: start/resize/stop the actual AGY terminal using a safe synthetic workspace; record dev dependencies, cold/warm build artifacts, installed/unpacked size, RAM, startup, build time, keyboard/clipboard/resize behavior and cleanup; repeat with both using comparable data and pin exact versions. Test a protected FlowState communication seam independently of either UI shell. Do not invoke real personal vault writes. The eventual desktop app, uninterrupted terminal recovery, native module packaging, and actual production integration remain untested.
